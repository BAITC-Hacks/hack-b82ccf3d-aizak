# AIZAK — объяснимый подбор подрядчиков для мероприятий

Проект команды AIZAK для HackAlem. Задача: **«Умный подбор подрядчиков (#79-lite)»**.

Официальный конкурсный репозиторий: [BAITC-Hacks/hack-b82ccf3d-aizak](https://github.com/BAITC-Hacks/hack-b82ccf3d-aizak).

## Текущее состояние

**Первый этап: требования, архитектура и план реализации.** В этом коммите добавляется документация. Приложение, обработчик датасета, интеграция с OpenAI API и тесты ещё не реализованы. Работа приложения, качество рекомендаций и время ответа пока не проверены.

Ниже описан план MVP, основанный на предоставленном тексте конкурсной задачи. Предлагаемые технические решения команды отмечены отдельно от требований. На момент подготовки этого README JSONL-датасет в репозитории отсутствует; количество записей и описание полей приведены по заданию и ещё не проверены по файлу.

## Проблема и целевая аудитория

Заказчик мероприятия уже выбрал город и получил каталог подрядчиков. Ему нужно выбрать несколько подходящих исполнителей и понять различия между ними: кто доступен на дату, соответствует формату и ограничениям заказа, чем обоснована каждая рекомендация.

Целевая аудитория — частные заказчики и организаторы мероприятий в Казахстане, подбирающие ведущего, фотографа, банкетный зал или подрядчика другой категории. AIZAK планируется как помощник внутри существующего каталога.

Ценность продукта — до трёх обоснованных рекомендаций с конкретными фактами из профилей и понятное объяснение ситуаций, когда подходящих кандидатов мало или нет.

## Основные требования конкурсного задания

| Область | Требование |
| --- | --- |
| Обязательный ввод | Город, дата мероприятия, тип мероприятия, категория подрядчика, бюджет в тенге |
| Необязательный ввод | Длительность в часах и язык |
| Результат | Не более трёх карточек: имя, категория, город, цена и объяснение в 1–2 предложениях |
| Объяснение | Конкретные совпадения по бюджету, формату, языку, длительности или смыслу описания; без универсальных рекламных фраз |
| Занятость | Подрядчик с выбранной датой в `busy_dates` исключается; правило распространяется и на площадки |
| Мало подходящих | Показать фактическое количество и объяснить, почему оно меньше трёх |
| Воспроизводимость | Один и тот же запрос даёт один и тот же порядок карточек |
| Состояния выдачи | Явно различаются: подобрали; в городе нет такой категории; категория есть, но ни один кандидат не проходит условия |
| Скорость | Ориентир из задания — ответ до 10 секунд; это целевой показатель, а не измеренный результат |

В задачу не входят бронирование, заявки и уведомления подрядчикам. Дообучение модели на 66 профилях не планируется. В задании приоритет качества объяснений выше сложности интерфейса.

## Данные и план обработки

Источник: предоставленный организаторами `hackathon-dataset-anonymized.jsonl`. По описанию задания он содержит 66 анонимизированных профилей, включая 13 полностью синтетических. Также предусмотрены CSV и HTML-превью, но основной формат MVP — JSONL.

| Поля | План использования |
| --- | --- |
| `id`, `anon_name` | Идентификация профиля, отображаемое имя и разрешение равенства при сортировке |
| `categories` | Проверка принадлежности выбранной категории |
| `city` | Проверка города; в описании данных указаны Алматы, Астана и Зарубежье |
| `price_from_kzt` | Проверка стартовой цены относительно бюджета; в карточке сохраняется обозначение «от» |
| `event_formats` | Проверка формата: свадьба, той, корпоратив, конференция, юбилей или день рождения |
| `languages` | Проверка выбранного языка, если пользователь его указал |
| `max_hours` | Проверка длительности; `null` означает, что работа не привязана к присутствию на площадке |
| `busy_dates` | Исключение занятого подрядчика на конкретную дату |
| `description` | Источник индивидуальных особенностей и фактов для объяснения |
| `synthetic`, `city_imputed`, `price_imputed` | Отображение происхождения профиля и восстановленных значений |

План загрузчика: прочитать UTF-8 JSONL построчно, проверить типы, уникальность `id`, даты и обязательные поля; сообщать о некорректной строке с её номером. Недостающие факты не восстанавливать выдуманными значениями.

Календари по заданию охватывают **23.09.2026–31.12.2026**. Предлагаемое правило MVP: для даты вне этого окна сообщать о недостаточности данных, а не считать подрядчиков свободными. Свободная дата внутри окна означает отсутствие записи о занятости в предоставленном календаре, а не подтверждённое бронирование.

Высокая занятость в декабре — ожидаемая особенность данных. Пустые результаты не следует скрывать добавлением неподходящих исполнителей. Если команда добавит свои профили, они будут помечены `synthetic: true`, храниться отдельно от исходного набора и явно отличаться в интерфейсе от профилей организаторов. Исходные синтетические профили тоже сохранят свою маркировку.

## Предполагаемый пользовательский сценарий

1. Пользователь указывает город, дату, формат, категорию и бюджет; при необходимости добавляет язык и длительность.
2. Приложение проверяет ввод и наличие категории в каталоге выбранного города.
3. Алгоритм исключает кандидатов, не соответствующих условиям, и сохраняет причины исключения.
4. Пользователь получает до трёх карточек с ценой «от», особенностями и индивидуальными объяснениями.
5. Если кандидатов меньше трёх или нет, интерфейс объясняет ситуацию словами. Условия запроса автоматически не ослабляются.
6. Пользователь может изменить дату и увидеть изменение доступности. Для демонстрации будет подобрана пара дат, на которых состав выдачи действительно меняется из-за календаря.

## Архитектура MVP — запланировано

```text
Форма Streamlit
    → валидация запроса
    → загрузка и проверка JSONL
    → выбор города и категории
    → фильтрация по условиям + причины исключения
    → воспроизводимая сортировка и выбор до 3 профилей
    → сбор проверяемых фактов
    → объяснения через OpenAI API либо резервный шаблон
    → карточки и сообщение о состоянии выдачи
```

Логику подбора планируется отделить от интерфейса и сетевого API в функцию `recommend(request, profiles)`. Её результат содержит статус, упорядоченные идентификаторы, факты для объяснений и причины исключения. Это позволит тестировать подбор без браузера и API-ключа.

### Фильтрация и воспроизводимый порядок

Предлагаемые правила реализации:

- Выбранная категория должна входить в `categories`, город — совпадать с запросом.
- Дата не должна входить в `busy_dates`.
- `price_from_kzt` должна быть не выше бюджета. Цена «от» не гарантирует окончательную стоимость заказа.
- Формат должен входить в `event_formats`.
- Указанный язык должен входить в `languages`; отсутствие пожелания по языку не исключает профиль.
- При заданной длительности числовое `max_hours` должно быть не меньше запроса. `null` не превращается в ноль и не означает неограниченное присутствие.
- Базовый приоритет MVP: стартовая цена по возрастанию, затем нормализованный уникальный `id`. Это техническое решение команды, а не требование организаторов и не оценка качества подрядчика.
- При неизменных данных, запросе и версии правил порядок будет определяться кодом. Генерация текста не сможет менять выбранных подрядчиков и их порядок.

Причины исключения сохраняются по профилям. Один профиль может нарушать несколько условий; статистика по причинам не будет представляться как сумма разных людей. Наличие категории проверяется до остальных ограничений, чтобы различать два вида пустого результата.

### Использование OpenAI API — запланировано

Модель будет получать параметры заказа и факты только о выбранных кандидатах: значения полей и релевантные фрагменты описаний. Планируется один запрос для объяснения всех карточек, структурированный ответ с `id` и текстом и проверка соответствия идентификаторов.

Каждое объяснение должно связывать особенности конкретного профиля с запросом. Нельзя придумывать отзывы, рейтинг, опыт, скидки, гарантированную стоимость или доступность вне предоставленного календаря. Текст описания обрабатывается как данные, а не как инструкции для модели. Соблюдение JSON-схемы само по себе не подтверждает правдивость объяснения.

Планируются ограничение ожидания API, проверка ответа и резервные объяснения из исходных фактов при ошибке или отсутствии ключа. Интерфейс должен отличать AI-объяснение от резервного режима. Кэш при реализации будет учитывать запрос, версию данных, модель и версию шаблона запроса.

Конкретная модель ещё не выбрана. Её идентификатор будет задаваться через `OPENAI_MODEL` после проверки доступности, качества и времени ответа. Вызовов API в этом коммите не выполнялось.

## Установка и запуск

Доступ к приватному конкурсному репозиторию необходим для клонирования:

```powershell
git clone https://github.com/BAITC-Hacks/hack-b82ccf3d-aizak.git
```

До объединения изменений следует перейти в ветку с нужной версией проекта. Этот README публикуется в ветке `docs/readme-initial`.

После реализации файлов, добавления датасета и фиксации зависимостей планируется такой запуск в Windows PowerShell:

```powershell
py -3.11 -m venv .venv

# Для AI-объяснений задайте собственный ключ и проверенный идентификатор модели:
```

Значения в кавычках — заглушки. Ключи не должны попадать в Git; они будут читаться из переменных окружения. При реализации необходимо подтвердить поведение без API-ключа и обновить этот раздел по фактически проверенному запуску.

## Тестирование и критерии готовности

**Тестов приложения пока нет, они не запускались.** Планируется следующая проверка:

- Занятый подрядчик и занятый банкетный зал исключаются на выбранную дату.
- Проверяются город, членство в категории, формат, бюджет на границе и выше границы, язык и длительность.
- `max_hours: null` корректно обрабатывается; отсутствие необязательных параметров не создаёт дополнительных ограничений.
- Количество карточек не превышает трёх; выдачи из нуля, одного и двух профилей объясняются словами.
- Различаются отсутствие категории в городе и отсутствие кандидатов, проходящих условия.
- Повторные запросы и изменение порядка строк во входном файле не меняют порядок результата при тех же данных.
- Некорректный ввод, дата вне окна календаря, ошибочная строка JSONL и повторный `id` обрабатываются явно.
- Ошибка, тайм-аут или отсутствие ключа API включают резервное объяснение без изменения состава выдачи.
- Тексты проверяются на соответствие фактам и индивидуальность; структурированный формат не заменяет эту проверку.
- Измеряется полное время ответа, включая первый запрос без кэша, относительно ориентира до 10 секунд.

Целевая команда после создания тестов и зависимостей:

```powershell
.\.venv\Scripts\python.exe -m pytest
```

Для живой демонстрации по заданию необходимо подготовить плотную категорию на осеннюю дату, редкую категорию и запрос без результата. Дополнительно команда планирует показать оба вида пустой выдачи и один запрос на двух датах с изменением состава из-за занятости. Точные запросы будут подобраны по реальному датасету; сейчас они не подтверждены.

Отдельная ручная проверка: убрать имена из объяснений и проверить, можно ли связать каждый текст с фактами его карточки. Финальная проверка воспроизводимости — установка и запуск из чистого клона по актуальному README.

## Ограничения и дальнейшее развитие

- Это начальный проектный документ; работающий сервис, тестовое покрытие и достигнутая скорость пока не заявляются.
- 66 профилей и ограниченное окно календаря не описывают весь рынок. Данные анонимизированы; часть профилей синтетические, часть значений восстановлена.
- Стартовая цена не равна согласованной стоимости услуги. Наличие свободной даты в данных не является гарантией бронирования.
- Базовая сортировка по цене не оценивает профессиональное качество; рейтинги и отзывы, отсутствующие в данных, не используются.
- AI-объяснения зависят от доступа к API и могут содержать ошибки, поэтому нужны проверка фактов и резервный режим.
- После выполнения обязательных требований можно рассмотреть семантическое ранжирование описаний с фиксированной версией признаков и проверенные предложения изменить отдельное условие запроса.

Приоритет разработки следует заданию: **качество объяснений → честная работа с редкими категориями, занятостью и пустой выдачей → скорость → интерфейс**. Документация и воспроизводимость оцениваются отдельно и обновляются вместе с реализацией.
